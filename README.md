# MarkItDown Mac

A native macOS drag-and-drop app that wraps the [markitdown](https://github.com/microsoft/markitdown) Python tool. Drop a file (PDF, Office document, HTML, image, CSV, etc.), get Markdown back — suitable for feeding into LLM pipelines.

The app bundles its own self-contained Python 3.12 runtime with `markitdown` installed inside `MarkItDown.app`. It does not use or depend on the system Python.

Built for personal/local use only: no Apple Developer account, no notarization — the app is ad-hoc codesigned (`codesign -s -`).

## Architecture

- **UI**: SwiftUI app (`app/Sources/MarkItDownMac/`), built with Swift Package Manager, not an Xcode project.
- **Conversion engine**: a vendored copy of the `markitdown` Python package (`engine/vendor/markitdown/`, from the `packages/markitdown` subfolder of the [paddingtonil/markitdown](https://github.com/paddingtonil/markitdown) fork), installed into a standalone CPython runtime downloaded from [astral-sh/python-build-standalone](https://github.com/astral-sh/python-build-standalone).
- **Bridge**: the app shells out to the bundled `python3` running `engine/convert_driver.py <file>` as a subprocess and captures stdout (Markdown) / stderr (errors) via `Process` + `Pipe`. See `app/Sources/MarkItDownMac/ConversionService.swift`.

## Build

```
./tools/build_app.sh
```

This:
1. Runs `swift build -c release` from `app/` (where `Package.swift` lives).
2. Runs `tools/build_python_runtime.sh`, which downloads the latest CPython 3.12 `aarch64-apple-darwin` "install_only" build from astral-sh/python-build-standalone (cached under `build/.cache/`), extracts it to `build/python-runtime/`, `pip install`s `engine/vendor/markitdown[pptx,docx,xlsx,xls,pdf,outlook]` into it, then installs `docling` and pre-downloads its model weights (see "Hybrid PDF engine" above) into `build/hf-cache/` by running one throwaway conversion at build time. Re-running this script is fast — it skips all of the above if `build/python-runtime` already reflects the current vendored source (tracked via a stamp file); set `FORCE_REBUILD=1` to force a full rebuild.
3. Assembles `build/MarkItDown.app` (`Contents/MacOS/MarkItDownMac`, `Contents/Resources/python-runtime/` + `convert_driver.py` + `hf-cache/`, `Contents/Info.plist`).
4. Ad-hoc codesigns the bundle: `codesign --force --deep -s - build/MarkItDown.app`.

The first build downloads ~24 MB (the Python runtime tarball), whatever `pip` needs for `markitdown`'s extras (pandas, lxml, pdfminer, etc.), `docling`'s own dependency stack (PyTorch + friends, roughly 1.2GB), and its ~530MB of model weights — this can take several minutes on first run and pushes `build/python-runtime` to ~1.6GB and the full `MarkItDown.app` to ~2.6GB. Subsequent builds reuse the cached runtime and model cache as long as `engine/vendor/markitdown` hasn't changed.

## Run

```
open build/MarkItDown.app
```

Or run directly from source during development (uses `build/python-runtime` + `engine/convert_driver.py` + `build/hf-cache` relative to the project root instead of the bundle's Resources):


## Install and update

```
./tools/install_app.sh              # build, then install or update /Applications/MarkItDown.app
./tools/install_app.sh --no-build   # install the existing build/MarkItDown.app
```

There is no auto-updater (the app is offline by design): an update means rebuilding and re-running this script. The app's version is `SHORT_VERSION` in `tools/build_app.sh` (currently 0.2.0); the build number (commit count) and the commit hash, with `-dirty` if tracked files had uncommitted changes, are written to `Info.plist` (`CFBundleVersion`, `MarkItDownGitCommit`), so Finder's Get Info shows which build is installed. Build from a clean tree to get a hash without `-dirty`. The bundle is self-contained (own Python, converters and Docling models), so it does not depend on this project folder once installed.

`build_app.sh` deletes `build/MarkItDown.app` before re-creating it, so a failed build leaves no working app there. The installed copy is protected from that: the script verifies the new bundle (executable, driver, valid code signature, the bundled Python can import the converters, model cache present), copies it to a hidden staging path next to the destination, verifies the copy, then swaps it in, keeping the previous version until the swap is verified and restoring it if not. It refuses to proceed if the app is still running. Set `INSTALL_DIR=$HOME/Applications` if `/Applications` is not writable.

Importing the bundled Python writes `__pycache__` files for any module that has no cached bytecode, which invalidates the bundle's code signature; the script therefore runs it with `-I -B` (`-B` is required: isolated mode `-I` ignores `PYTHONDONTWRITEBYTECODE`) and checks the signature last. The same applies to any manual use of the bundle's Python: pass `-B`. If `build/MarkItDown.app` ever fails `codesign --verify --deep --strict` after manual use, re-sign it with `codesign --force --deep -s - build/MarkItDown.app`.

## Regression testing

```
./build/MarkItDown.app/Contents/Resources/python-runtime/bin/python3 tests/regression_test.py
```

Runs the real conversion pipeline against a fixed set of real-world documents with known-correct characteristics (a max Hebrew-orthography-violation count, specific text that must/must-not appear) and fails loudly if anything regresses. This exists because this project's history has repeatedly shown that a fix verified against the one document it was written for can silently break a *different* document that was already working -- see the Hebrew/RTL section below for several real examples, including one where a table fix regressed two previously-clean documents and was only caught because this exact kind of check was run by hand before shipping. **Run this after any change to `_pdf_converter.py` or `convert_driver.py`'s routing logic, not just a check against whatever document motivated the change.**

The fixtures live in `tests/regression_fixtures/` (gitignored -- personal documents copied there from stable locations, not meant for version control) rather than being referenced by their original path, because a file living in `~/Downloads` or similar can move or get cleaned up between sessions -- confirmed to actually happen once already. Pass `--full` to also run the slower Docling-routed English-document checks (several minutes); default is the fast Hebrew-path checks only (under two minutes total). Pass `--verbose` to print a failing check's full output. See the script's own docstring for how to add a new fixture.

Some documents are referenced in place instead of copied into the fixtures folder -- the commercial travel guides, the 145-page teacher workbook and the published science textbook booklet -- because their licences restrict copying; a "fixture not found" failure on those means the path moved (the booklet already has once), not that something regressed.

**Results are PASS, FAIL or WARN.** WARN ("inconclusive") is only possible for the slow Docling-routed checks, and only when the conversion times out or the process is killed by a signal (a native-library crash): neither says anything about output quality, and a longer timeout can't fix a crash. A slow check that finishes with wrong content, any ordinary driver error, and any problem at all on a fast check are always FAIL. WARN doesn't change the exit code, but inconclusive checks are listed at the end rather than buried, and re-running settles them.

A check can also assert that the converter's own validation warnings are *absent* (`must_not_warn`). That exists because some failures are recovered from silently: with per-page isolation (see "Post-conversion validation"), the CropBox bug that once wrecked a whole document now produces perfectly plausible text and shows up *only* as a "hit an internal error" warning naming the affected pages. Each check was confirmed to go red by re-introducing the bug it guards against in a throwaway copy of the converter, so a green run means the guard works, not just that it hasn't been tripped.

The runtime executes the *installed* copy of the `markitdown` package, not `engine/vendor/markitdown/src` directly: after editing the vendored source, reinstall it into the runtime (`<runtime>/bin/python3 -m pip install --force-reinstall --no-deps engine/vendor/markitdown`) or `tools/build_app.sh` before running this, otherwise the suite is testing the previous code.

## Post-conversion validation

Every conversion is followed by a small validation pass (`engine/convert_driver.py`) rather than just trusting whatever the converter returned. It currently flags: empty/near-empty output (likely a scanned document or a file with no extractable text); the image-coverage note `_pdf_converter.py` already generates (see below); and — for PDFs with substantial Hebrew content — a page-level extraction-fallback note (see "Per-page failure isolation" below) and a Hebrew orthography-violation *rate* (violations per 1,000 Hebrew letters, not a raw count — see below for why the distinction matters). `convert_driver.py` reports these as JSON (`{"markdown": ..., "warnings": [...], "needs_confirmation": bool}`, `warnings` empty when nothing was flagged) rather than raw Markdown text on stdout — `ConversionService.swift` decodes this into `ConversionOutput`.

A file with warnings but `needs_confirmation: false` (e.g. the image-coverage note — true of essentially every scanned diagram, not a sign anything went wrong) shows an amber "Converted*" tag and a warning line on its card instead of the plain sage "Converted" tag, but otherwise behaves like a normal conversion. A file with `needs_confirmation: true` — currently either the Hebrew-violation-rate check, when it's well above this project's own regression-fixture baselines, or the symbol-for-letter check described below — lands in a distinct `.needsReview` state instead: the card shows a "Needs review" tag and the content is available to inspect/copy, but it's excluded from "Save all" and isn't persisted across launches until the user explicitly taps "Use Anyway" (`ConversionViewModel.acceptReview`). The one real document that used to land here (a textbook booklet) turned out to be fixable at the source — see "Hebrew fonts whose ToUnicode map is wrong" in the RTL section — so the gate currently has no known positive case in the regression suite; the booklet's check only asserts that it no longer trips. For corruption of some other kind there is still no automatic correction on this machine (RapidOCR, docling's bundled OCR engine, doesn't recognize Hebrew script at all, and neither does macOS's own Vision-framework OCR as of the OS version this was tested on), so asking rather than silently delivering a possibly-corrupted result remains the honest option.

The Hebrew-violation check uses a *rate* (violations per 1,000 Hebrew letters) rather than a raw count. A raw count was left out of validation at first because even a clean document trips on legitimate abbreviations like `תנ"ך`, and a long document accumulates more of them than a short one; a rate removes document length as a confound. Measured on the six Hebrew regression documents (2026-10-08) it ranges from 0.31 to 1.78 per 1,000, while the one known-bad document (a corrupted font encoding) came out at 8.9; the threshold is 5.0. That is one bad data point, so the threshold is a judgement between the two, not a fitted value.

**The rate cannot see a symbol standing in for a letter**, because it only looks at Hebrew letters: a real document with 41 lines like `ני#וי` (for `ניסוי`) still read 0.74 per 1,000, and adding those lines to the rate would only have reached about 1.3, far under the threshold of 5. So there is a second, separate signal, counted in lines: a symbol (`#` or `&`) inside a Hebrew word or glued to its end (`_HEBREW_SYMBOL_SUBSTITUTION_PATTERN`), three lines or more. It matches 0 lines on the correct output of all seven Hebrew regression documents and 36 on the corrupt one; with the old rate check alone that corrupt output passed. Two candidate patterns were measured and rejected for the shipped check: a symbol at the *start* of a word (a hashtag such as `#ישראל` would trip it) and a digit glued after a word, which matched in two clean documents on legitimate text (`בעולם8`, a footnote marker, and `פעילות1:`). The threshold is a judgement between 0 and dozens, not a fitted value.

**Abbreviations are left out of the rate.** The counter splits a word at a gershayim or geresh, so the stem of `תנ"ך` or `עמ'` reads as a word ending in the regular form of a letter that has a final form: one violation each, on correct text. A generated Bible-lesson worksheet (681 Hebrew letters, nine such abbreviations) read 13.2 per 1,000 and landed in `.needsReview`. The driver now subtracts those stems (`_HEBREW_ABBREVIATION_STEM_PATTERN`) from the count it uses for the rate; the counter itself is untouched, because it also decides line direction in `_pdf_converter.py`. On the seven real documents this changes little (0.23 to 1.78 per 1,000 instead of 0.31 to 1.78; they held 0 to 14 such stems each), so the worksheet is the evidence that it matters, not they. The gate keeps its sensitivity: the same documents with every line mirrored read 75 to 92 per 1,000 before and after. That mirrored worksheet is now a standing positive check in the regression suite (`tests/synthetic_fixtures/hebrew_mirrored_lines.txt`), confirmed to fail when the rate gate is disabled.

**A scanned Hebrew PDF has no Hebrew letters for either check to look at.** With no text layer the Hebrew-fraction sample finds no letters, the file is routed to `docling`, and its OCR (which reads Latin and Chinese script only) returns noise such as `UUUILIO ¿LXI XU LALOA`; that used to be delivered as a clean conversion. So when the text came from `docling` *and* the sample of the text layer found fewer than 200 letters, the driver measures how much of the output reads as words: of the tokens containing a letter, the share that is a lowercase or Capitalised ASCII word (`_ocr_wordlike_fraction`). Below 0.3 the file lands in `.needsReview` with a message saying the app cannot read scanned Hebrew. Measured on two generated one-page scans (`tests/synthetic_fixtures/`): 0.00 for the Hebrew page, 0.95 for the English one. Those are clean renders, not real scans, so the threshold is a judgement inside a wide gap, not a fitted value; a scan in any other script the OCR cannot read (Russian, Arabic) is flagged the same way, which is correct. Readable OCR output gets no extra warning. Actually converting scanned Hebrew needs a Hebrew OCR engine, which the app does not have.

**Short text files in Windows-1255.** markitdown decodes `.txt`/`.md`/`.csv` by statistical charset detection, which needs more text than a short file has: a 26-byte Hebrew file came out as Cyrillic (`їьхэ Ґхьэ`), with no warning, because Windows-1251 and Windows-1255 keep their letters in the same byte range. `_detect_legacy_hebrew_charset` in the driver now checks first whether the Windows-1255 reading is plausible Hebrew (every byte defined, non-ASCII characters nearly all Hebrew and not glued to Latin letters, no vowel point without a letter before it, final-form letters almost never mid-word) and only then passes that charset to markitdown. Valid UTF-8, files with a byte-order mark and UTF-16 are never touched. Checked on 18 short samples: seven Hebrew ones accepted, and Russian, French, German, Greek and Arabic ones in their own legacy encodings all rejected. Files inside a ZIP do not go through this.

**CSV files that are not comma-separated.** markitdown's CSV converter splits on commas only, so a semicolon-separated file (what Excel writes under locales with a decimal comma) or a tab-separated UTF-16 one (Excel's "Unicode Text") came out as a one-column table with the separators left inside the cells. For `.csv` files the driver now checks whether the file reads consistently as comma-separated (every sampled row as wide as the header, at least two columns) and leaves it alone if so; otherwise it tries `;`, tab and `|` by the same test and hands markitdown a comma-separated UTF-8 copy in memory (`_normalize_csv`; no temporary file is written). Checked on 12 small files, including decimal commas, a delimiter inside quotes, semicolons inside the text of a comma-separated file, a single-column file and prose with stray semicolons (the last three are left untouched). A leading UTF-8 byte-order mark is also removed from the output of any conversion; it used to survive in front of the first word of a `.txt` file.

The weak spot of the rate check is small samples: a document with only a few hundred Hebrew letters is noisy (the math worksheet fixture has 562 and one decorative-spacing artifact alone puts it at 1.78), and below 500 letters the check is skipped. A sparse document that crosses the threshold lands in `.needsReview`, where "Use Anyway" is one tap, so the cost of a false alarm is small, but it is still noise. Extending validation should keep the same bar as before: a warning (and especially `needs_confirmation`) should mean something worth knowing, not routine noise a user learns to ignore.

### Per-page failure isolation

Every page in a PDF goes through its own try/except in `_pdf_converter.py`'s main loop now, after a real document exposed a serious failure mode: one page's CropBox had a non-zero-origin bounding box (top at -7.8pt instead of 0), which `_detect_row_bands` didn't account for and raised a `ValueError` on. Because there was no per-page isolation at the time, that single page's exception propagated out of the *entire* per-page loop and silently downgraded the *whole* document (145 pages, not just the one) to a much cruder whole-document `pdfminer` fallback with none of this file's band/column/table-aware extraction -- which is what actually produced a badly-scrambled conversion throughout, not a Hebrew-specific bug. A page that hits an exception now falls back to its own plain `page.extract_text()` only, and the rest of the document keeps using the full extraction pipeline; the affected page numbers are surfaced as a validation warning (see above) so a future not-yet-seen per-page edge case stays visible instead of silently degrading quality with no signal at all.

## Supported formats (v1)

Every package in the runtime is pinned to the version in `tools/runtime-constraints.txt` (117 packages, recorded from the tested runtime), which `tools/build_python_runtime.sh` passes to pip as constraints; before that each rebuild installed the newest `docling` and dependencies. The model weights downloaded into `hf-cache` at build time are not pinned. See the file's header for upgrading on purpose.

Backed by the extras installed into the bundled runtime (`pptx, docx, xlsx, xls, pdf, outlook`), plus markitdown's always-on converters:

- Plain text, Markdown, HTML, CSV, JSON, RSS/Atom feeds, Jupyter notebooks (`.ipynb`), EPUB, ZIP (converts each contained file)
- PDF (`.pdf`)
- Word (`.docx`), PowerPoint (`.pptx`), Excel (`.xlsx`, `.xls`)
- Outlook messages (`.msg`)
- Images — metadata/EXIF extraction only (no captioning, see below)
- **Not supported, on purpose:** audio (`.wav`, `.mp3`, `.m4a`, `.mp4`) and YouTube transcripts. See "Transcription removed" under Known gaps.

### Hebrew/Arabic (RTL) PDFs

PDFs can exhibit three independent, unrelated extraction bugs for Hebrew/Arabic text, and — in documents assembled from multiple source files (e.g. a booklet compiling worksheets from different authors/tools) — different pages, or even different lines, can have any combination of them at once:

1. **Mirrored (visual-order) text.** Some PDF producers (notably browsers' "print to PDF" for RTL web pages) store Hebrew/Arabic glyphs in left-to-right visual order in the content stream rather than logical reading order. `pdfminer`/`pdfplumber` extract characters verbatim in that stream order, which mirrors the text (e.g. `אפשר` comes out as `רשפא`) while leaving embedded numbers/Latin text correctly ordered.
2. **A font-encoding swap.** Some PDFs embed a subsetted Hebrew font whose character encoding has the glyphs for `ל` (lamed) and `ם` (final mem) mapped to each other's Unicode code points, so every extracted `ל` is actually `ם` and vice versa (e.g. `לבחור` extracts as `םבחור`).

3. **A wrong ToUnicode map.** Some fonts carry correct glyph names but a ToUnicode CMap that maps each code to the wrong character, so the extracted text is unrelated to what the page shows. This one is fixed at font-loading time, not per line — see "Hebrew fonts whose ToUnicode map is wrong" below.

`engine/vendor/markitdown`'s `_pdf_converter.py` patches the first two at the text level. For each extracted line containing Hebrew/Arabic characters, it builds up to four candidate readings — the line as-is, flipped through the Unicode Bidi Algorithm (`python-bidi`'s `get_display`), with ל/ם swapped, and both — and picks whichever scores as the most plausible Hebrew: fewest violations of the rule that a final letter form (ם ן ף ץ ך) can only legally be the last character of a word, tie-broken by matches against a small built-in list of common Hebrew function words (for short lines with no final-letter evidence either way). Trying all four combinations per line, rather than deciding order and letter-identity independently, matters because the font-swap corruption can throw off the order decision if handled first. This is a local patch on top of the vendored source, not upstream `markitdown` behavior — worth remembering if `engine/vendor/markitdown` is ever re-synced from a newer upstream release.

**Short lines (headings, table-of-contents entries) still need document-level context.** A heading like `הנחות יסוד` ("Founding assumptions") has no word ending in a final letter and no match in the common-word list, so per-line scoring alone sees zero evidence either way and defaults to "leave it alone" — wrong whenever the underlying line actually is mirrored, and headings/TOC entries hit this blind spot constantly on real documents. The fix: within one extraction call (typically a whole page's text, sometimes a whole document), lines that *do* get a decisive verdict vote on flip/swap, and every undecided line falls back to that majority — a mirrored heading with no evidence of its own still gets corrected because the body-text paragraph around it did have some. Caught and fixed against an 86-page real-world curriculum PDF where every section heading and every line of its table of contents was silently staying mirrored while the body prose around them was already being fixed correctly.

Known residual limitations, both low-frequency and left as-is rather than chased to zero:
- **Bracket-pairing edge case:** parenthetical asides that straddle a line-wrap in mixed Hebrew/English text can occasionally land with misplaced bracket characters (a hard Unicode Bidi bracket-pairing case) — cosmetic only.
- **Swaps that land in a still-valid position rely entirely on the common-word list.** The font-swap detector's positional rule (final letter forms only legally end a word) can't see a swap that happens to land in another still-valid position (e.g. a word that should end in `ם` instead ending in the equally-valid-looking `ל`) — that case is only caught if the common-word tie-break happens to have a matching entry, and Hebrew's attached prefixes (`ו`/`ב`/`ל`/`כ`/`מ`/`ה`/`ש`, stackable up to two) mean a real word essentially never appears in the extracted text in its bare dictionary form, so the word list matches after stripping up to two leading prefix-set letters, not by exact match. Caught in practice: `וגודם המספריל` (originally invisible to the positional rule — both readings are position-valid) only resolved to the correct `וגודל המספרים` once `מספרים` was in the word list *and* prefix-stripping let it match against the actual token `המספרים`. This is not a general solution — any word outside the ~170-entry list, or a document that happens not to repeat its keywords elsewhere in a way that reinforces the tie-break, can still slip through. A genuine fix would need a real Hebrew dictionary/wordlist rather than this small curated set — reasonable for now, not exhaustive.

### Hebrew fonts whose ToUnicode map is wrong

A Hebrew school-textbook booklet (104 pages) came out as Hebrew letters mixed with ASCII punctuation and digits — unreadable, and not repairable by the mirror/swap heuristics above because the information was lost before they ran. Inspecting its fonts showed why. Each typeface was embedded as two subsets: a Latin one (MacRoman encoding, no ToUnicode, decodes fine) and a Hebrew one whose `/Encoding /Differences` array held correct Adobe Glyph List names for every code (`he`, `nun`, `alef`, … and the niqqud: `qamats`, `sheva`, `hiriq`), alongside a `/ToUnicode` CMap that was generated from the character *codes* rather than the glyphs (33 → `!`, 34 → `"`, 48 → `0`, …) and left about a third of the codes out. pdfminer consults ToUnicode first and only falls back to the glyph names for codes it doesn't mention, so the omitted codes came out as real Hebrew and the wrongly-mapped ones as ASCII — exactly the mixture seen.

OCR was not an option: RapidOCR (docling's engine) has no Hebrew model and produced Latin-letter gibberish when forced to OCR full pages, and macOS Vision does not list Hebrew among its supported recognition languages on the OS version tested. The correct text was simply in the PDF already. `_install_hebrew_glyph_name_priority` wraps `pdfminer`'s `PDFSimpleFont.__init__` so that, for a code whose glyph name resolves to a Hebrew character *and* whose ToUnicode entry is **not** Hebrew, the glyph name wins. The rule is deliberately narrow: ToUnicode maps that agree, or that point at a different Hebrew character, are left alone, as are fonts with fewer than three Hebrew-named codes. A few names pdfminer's glyph list lacks (`maqaf`, `geresh`, `gershayim`, `sofpasuq`) are supplied by a small table. Because it patches the font class itself, the whole-document `pdfminer` fallback benefits too. Effect on that booklet: 313 violations → 60, a rate of 8.9 → 0.74 per 1,000, and it no longer trips the "Needs review" gate.

**The first version of this fix was incomplete, and the validation could not see it.** One typeface family in the same booklet came from a second export tool that spells its glyph names differently from the Adobe Glyph List: `samech` for `samekh`, and `final_mem`, `final_nun`, `final_kaf`, `final_pe`, `final_tsadi`, `hataf_patah`, `tav_dagesh` with underscores (pdfminer reads `_` as a ligature separator, so `final_mem` means "final" + "mem" to it and fails). Exactly the samekh and the final-form letters stayed wrong, and as ASCII symbols, not Hebrew: `ניסוי` came out `ני#וי`, `ארגון` came out `ארגו9`, `סוג` came out `&וג`. The violation counter never noticed, because it only looks at Hebrew letters — 41 lines were affected and the rate still read 0.74 per 1,000. Fixing it needed two things beyond the alias table (`_HEBREW_GLYPH_NAME_ALIASES`, containing only names actually observed): the decision has to come from the glyph *name*, because pdfminer builds its code table starting from StandardEncoding and silently keeps that default (code 35 stays `#`) for any name it cannot resolve, so asking that table first returned the stale `#` and never reached the resolver; and the stale entry has to be overwritten, not set-if-missing. After it, 4 such lines remain, all of a different kind (below). The regression check now asserts that four regular expressions describing "a symbol where a Hebrew letter should be" match nothing; each matched 13 to 35 lines of the old output.

Caveats. It monkeypatches a third-party class (tested against `pdfminer.six` 20260107): if a future release changes those internals, the failure mode is the heuristic silently doing nothing, which the booklet's regression check would catch. It covers simple fonts only; Type0/CID fonts are structured differently and are untouched. A name that matches neither the Adobe list nor the aliases (`vavdageshhebrewaltone`, seen in 2 fonts) stays unresolved on purpose, rather than guessed: it leaves one visible `@` standing for a `ו` in the phrase "שימו לב" on the last page. And that booklet still has defects that are *not* encoding problems: sidebars on pages the word-position "form" path handles (see "Sidebars"), stray spaces inside niqqud-heavy words (`כס ף`), a stray `G` from a symbol-font glyph, a decorative `ø` ornament inside the headings (a dingbat in the heading font, not a corrupted letter), empty table stubs from decorative boxes, three `(cid:N)` placeholders for what looks like a dash glyph, and one scrambled line on a page about fertilizers.

### Punctuation and list markers on reordered lines

Reordering a mirrored line with the bidi algorithm puts each Hebrew run in the right order but leaves neutral characters where the visual layout had them. A sentence's final period sits at the visual *left* end of a right-to-left line, which is the *start* of the extracted string, so `מהרה, … מוחלטת.` came out as `.מהרה, … מוחלטת`. Measured on seven real documents, 19–49% of Hebrew lines began with sentence punctuation and almost none ended with it. The same reordering stranded list numbers (`.4 text` for `4. text`), put a page number after its period (`.98 …שבעמוד` for `…שבעמוד 98.`), and detached bullets from their text (a booklet had 261 lone `•` lines).

`_tidy_reordered_hebrew_line` fixes these on lines whose chosen reading was flipped (the artifact comes from the flip): leading punctuation moves to the end, `.N text` becomes `N. text`, `.N. text` becomes `N. text.`, punctuation in front of a number moves to the end, a bullet stranded at either end becomes a Markdown `- ` item, table-of-contents dot leaders become `…`; `_merge_detached_bullets` joins a lone `•` to the line after it. Result on the seven documents (counting the `- .` form too): lines starting with punctuation 903 → 20 in the curriculum, 995 → 14 in the workbook, 1,240 → 18 in the booklet, 108 → 13 in the policy document; lone bullets in the booklet 261 → 6.

Two things went wrong on the way, and are why the pass looks the way it does:

- **A cosmetic pass must not feed layout decisions.** The first version ran inside every call to `_fix_hebrew_extraction`. The form path classifies a row as a paragraph partly by the *length* of its fixed text, and the pass shortens a dot-leader line from ~90 characters to a few, so plain-text regions of two documents silently turned into tables. Tidying is now opt-in (`tidy=`, `merge_bullets=`, or `_fix_hebrew_page_text`) and used only where text goes straight into the output; the form path keeps untouched `text` for classification and writes a separate `display_text`. Cell-per-line input gets the per-line tidy but never the bullet merge, which changes the line count.
- **The numbering rule was wrong about a third of the time when applied naively**: `.98 …שבעמוד` is a page reference, not list item 98. A random sample of the lines each rule rewrites showed it; the last word of the text (`עמוד`, `בעמ'`, `ה"ש`, `פרק`…) now decides which reading applies. Only unambiguous bullet glyphs (`• ● ▪`) are merged: lone `-`, `–` and `?` lines in a math worksheet are not bullets.

How it was verified: after stripping whitespace, punctuation and bullet markers, every document contains exactly the same characters before and after (nothing lost or invented), and the number of table rows is identical in all seven (no region changed layout). Regression checks pin it: no Hebrew line starts with punctuation in the policy and Davidson documents (108 and 28 lines before), the workbook's opening sentence ends with its period, and a booklet bullet is one `- …` item. Disabling the tidy in a throwaway copy makes exactly those checks fail.

Not covered: text from the word-position "form" path's table cells and mirrored fragments that were never flipped (e.g. `?הרעשהה`, which is `ההשערה?` backwards) are left alone; the workbook's 26 bullets stay detached because they are separate objects that land after the whole list; and its one-line-per-paragraph fragmentation (68% of its lines are isolated) needs paragraph reflow from page geometry, which this text-only pass cannot do.

### PDFs with image-based numerals/content

Some worksheets/documents render numbers (or other content) as individual images rather than font glyphs — e.g. decorative/hand-drawn-style numeral graphics rather than a text numeral. No text extraction approach (this app's, or any other, including Adobe's own copy-paste) can recover that content as text; it's invisible to the text layer entirely. This showed up on a real-world math worksheet PDF, where one page alone had ~200 embedded images and zero digit characters in its text layer despite clearly showing arithmetic problems when rendered. The only way to actually recover that content is OCR (image recognition) — see the OCR item below, which is exactly this same gap.

This isn't limited to numerals — diagrams, illustrations, and decorative graphics are equally invisible to text extraction, and **upstream `markitdown` gave no indication any of this was skipped**: the Markdown output looked like a complete transcription even on a page that was mostly pictures. `_pdf_converter.py` now counts `page.images` per page and appends a summary to the end of the document — total image count, page count, and a per-page breakdown — whenever a PDF has any. It doesn't recover the content (still needs OCR for that), but it makes the gap visible instead of silent, so a reader comparing the Markdown against the source PDF can see exactly which pages had visual content that didn't make it in, rather than only noticing something was missing by manually cross-checking. On the math worksheet PDF this surfaced 4,573 images across 38 of its 39 pages — a scale that wasn't obvious at all from the Markdown output alone before this change.

### Worksheet-style PDFs: empty grids and icon-font glyphs

Two more artifacts specific to worksheet/form-style PDFs (grids, answer boxes, checklists), also found via the math worksheet PDF above, both fixed in `_pdf_converter.py`:

- **Blank answer grids misdetected as data tables.** The column-alignment heuristic that detects "form-style" tables doesn't distinguish a real data table from a blank grid meant for students to fill in by hand — both are aligned columns of short cells. Rendering a totally empty grid as a full Markdown table is pure noise (dozens of `|     |     |     |` rows carrying no information) that can dominate a worksheet-heavy document's output. Fix: after building a table, if under 20% of its cells actually have content, skip the table framing and emit only the non-empty cell values as plain text (dropping empty rows entirely) instead — a real, denser table (or a grid where the fill pattern itself is the content, e.g. an X/O game board) stays well above that threshold and still renders as a proper table.
- **Icon-font glyphs counted as "content."** Some PDFs use a Wingdings/Symbol-style icon font (checkboxes, bullets, decorative marks) whose glyphs are mapped into the Unicode Private Use Area (U+E000–U+F8FF) with no real meaning outside that specific font — extracted verbatim, they're unreadable codepoints that also happen to make an otherwise-blank table cell look "filled," which defeated the fix above until this was caught. These characters are now stripped from all extracted text (not just inside tables) since they're never meaningful once separated from their source font.

### Bordered tables (official/government-style documents)

Found on a real Hebrew Ministry of Education document (a bordered 4-column schedule table): the word-position heuristic in `_extract_form_content_from_words` never recognized the page as tabular at all -- it produced ~100 fragmented, unordered lines with no table structure. The page has real vector-drawn cell borders (123 `rects`), which pdfplumber's own built-in `page.find_tables()` uses directly -- unambiguous geometry beats guessing from word alignment. `_extract_page_with_line_tables` now tries that first (only for pages with genuine line-detected row/column structure; falls through to the existing word-position heuristic otherwise), and builds a proper Markdown table from the result.

This surfaced a second, more subtle bug while fixing the first: table cells were being Hebrew-RTL-fixed one at a time, so a short cell with no order evidence of its own (a two-word date-range header like "אפריל-מאי") had nothing to vote on and often stayed wrong, even sitting right next to a long, correctly-fixed cell in the same table. Fix: in `_markdown_table_from_cells` (used for line-detected tables), all of a table's cells are now fixed together in one pass (one cell per line) -- the same cross-line majority-voting mechanism already used for headings within a page -- so a short cell can borrow the verdict from decisive cells elsewhere in the same table. The same combined-fix approach was also tried in the older word-position heuristic's `extract_cells` (rows there often mix real content with sparse numeric/symbol fragments) and reverted after it mis-flipped otherwise-fine cells and regressed two previously-clean real documents; that path still fixes cells one at a time.

**RTL column order.** Markdown tables always render columns in the literal left-to-right order they're written in the source -- confirmed as a real, visible bug on the schedule table above: a lone bullet-marker column that visually belongs on the right (read first in Hebrew) was landing as the *last* Markdown column instead. `_reverse_rtl_table_columns` now reverses a table's column order whenever its content is Hebrew-dominant, applied to both table paths.

**A serious regression, caught only by the existing regression suite.** Extending line-table detection to real documents (not just the one it was built against) hit a genuinely different table shape: a Hebrew curriculum PDF has real bordered tables too, but they're grading-rubric matrices with dense multi-paragraph cells (up to 15 embedded lines of prose each) -- a fundamentally different case from a short-cell schedule table, and treating a whole such cell as "one line" for the RTL fix produced far worse results (violations roughly 10x) than the existing multi-column-aware plain-text path this same document was already handled well by. Fixed with a density guard in `_extract_page_with_line_tables`: it now skips line-table extraction (falling back to the existing heuristics) when a page's detected tables have dense, multi-paragraph cells on average, keeping this fix scoped to the short-cell tables it was actually validated against. A second issue found in the same investigation -- and the one actually responsible for most of the regression -- was a plain bug: one of two near-identical code paths for the text *around* a detected table was missing the Hebrew-fix call entirely (a copy-paste/refactor gap, not a design flaw), silently leaving that text mirrored. Both are why this document's violation count is checked on every change, not just the document a fix was written against -- a fix verified against one real document can still regress another.

### Multi-column layouts (magazines, guidebooks)

pdfplumber's default text extraction reads a page primarily top-to-bottom. On a genuinely single-column page that's correct; on a **two-column page** (common in magazines, guidebooks, newsletters) it interleaves the two columns by vertical position instead of reading column one fully and then column two — every individual word extracts correctly, but the result is unreadable nonsense (column A's line 1, column B's line 1, column A's line 2, ...). Found on a real 128-page Lonely Planet guidebook PDF: prose that read perfectly fine sentence-by-sentence in isolation was, in the actual output, shuffled together with an unrelated sidebar column into gibberish.

Fixed in `_pdf_converter.py` (`_detect_column_gutter` / `_extract_plain_page_text`): for the plain-text extraction path, each page is checked for a page-spanning vertical gap in character coverage (projecting every character's x-range onto the x-axis regardless of y-position) that sits roughly in the middle half of the page width and is comfortably wider than ordinary word-spacing — the signature of a column gutter. When found, the page is cropped into a left and right region and each is extracted separately (via pdfplumber's own `extract_text()`, reused rather than reimplemented) and concatenated in reading order. When no confident gutter is found — the common single-column case — behavior is unchanged. Verified with zero false positives across three single-column Hebrew PDFs already covered above (no gutters detected, no change in output) before trusting it on real two-column content.

**This needed a second pass** (`_detect_row_bands`): a page mixing a full-width headline with a two-column body below it defeated the gutter search entirely, because the search originally spanned the *whole* page height — a single full-width row anywhere (the headline) is enough to rule out any gutter, even though the body region clearly has one. Found on a real annual travel-planner PDF: its table-of-contents page has a full-width title above a two-column list, and the two-column part stayed scrambled even with the fix above in place. Fix: first split the page into horizontal bands wherever there's a page-width vertical gap wider than normal line-spacing (isolating the headline from the body, or a full-width photo caption from the two-column text around it), then look for a column gutter independently *within* each band. Column-splitting is also now recursive within a band (`_extract_region_text`, capped at 2 levels / 4 columns) — a genuine three-column region often has its widest gap between column 1 and columns 2+3 together, and re-checking each resulting piece for a further gutter catches that, rather than only ever making one cut.

An unexpected side benefit: a photo credit ("JOANNA L DAVIS") was extracting as "SIVAD ANNAOJ L OJ" — a different, unrelated-looking symptom (reversed English text, on a document with no RTL content at all) — that turned out to share the same root cause. It's very likely a rotated/vertical caption sitting in a narrow strip that was getting entangled with the surrounding two-column content in the old single-pass extraction; isolating it into its own band+column fixed it as a byproduct, without any code specifically about rotated text.

**Sidebars need a different rule** (`_detect_sidebar_gutter`). The column detector only accepts a gutter whose midpoint is in the middle half of the region, which suits two-column text but not a narrow note column at the page edge. A textbook's teaching-note sidebar had a clear 29pt gap whose midpoint sat at 23% of the page width, so its lines were interleaved one by one with the story beside it, even splicing into the middle of a line. Widening the window would be wrong, because an off-centre gap is also what a label/value layout or a table of contents looks like, and splitting those would separate every label from its value. What tells them apart is baselines: in a label/value layout both sides share them, while a sidebar has its own font size and leading. So the rule needs a gap of at least 20pt, a narrow side (at most 40% of the width) holding at least 80 characters on at least 5 lines, and fewer than half of those lines sharing a baseline with the other side. A sidebar is emitted *after* the main text instead of left-to-right, whichever side it sits on, since it is an aside. The text around a page's tables never used row bands, so a full-width element (the textbook's question banner) filled the gap and hid the sidebar; it is now banded first, but only when a band actually contains a sidebar, so no page without one changes.

Evidence for the rule: it fires on 0 of about 320 pages across the six Hebrew regression documents and on 4 of the booklet's 104 pages (pages 2, 16, 50 and 88), and the three of those I inspected were real sidebars. The output of all six other documents is byte-identical before and after. Limit: a page that takes the word-position "form" path because it contains a real table never reaches this code, and page 50 is one — its sidebar is still interleaved, and some of its fragments come out mirrored.

**Row bands are clamped to the page.** `_detect_row_bands` puts a band boundary at the midpoint of each vertical gap, and text positioned outside the page (a printer's production slug below the trim edge) pushed that midpoint off the page, where pdfplumber refuses to crop. On a 76-page travel planner this raised on 26 pages; each fell back to plain extraction (visible only as the "hit an internal error" warning) and carried the slug as doubled-letter noise on every page (`00 CCoovveerr..iinndddd 11 66//55//2266 99::2277 AAMM`). Boundaries are now clamped to the page and a gap that clamps to nothing is dropped instead of becoming an empty band. Result on that planner: 26 degraded pages became none, the slug text is gone, section breaks appear, and a boxed passage that the plain fallback had not returned came through. The other eight test documents are byte-identical before and after. This is **not covered by a regression check**: that planner is normally converted by docling, so the suite never reaches this code with it; it only matters when docling fails and the markitdown fallback runs.

Known limits, not fully addressed:
- **Only whitespace gutters are detected.** Some pages have no character-free gap between columns at all — a genuinely tight-set layout, or a sidebar whose content happens to occupy exactly what would be the gutter at some row — and no gutter is found there even after banding. Confirmed on one page of the 128-page guidebook above: its main content band still has continuous character coverage across its full width with no gap anywhere, so it falls back to unsplit (still scrambled) extraction. A fully robust fix would need to also look for an actual vector rule line between columns (`page.lines`/`page.rects`) rather than relying on whitespace alone — not implemented.
- **Map/diagram label text is a fundamentally different, harder problem** and is not fixed by this: place-name labels scattered across a map graphic are a genuinely 2D layout (not a column), and extracting them in any coherent reading order isn't a column-detection problem — it would need real spatial clustering or OCR. Expect scrambled fragments (occasionally including a duplicated label) around map pages even with this fix in place.
- **A rare native-library crash** (a `recursive_mutex lock failed` abort inside a C dependency, not Python-catchable) was observed on the 128-page guidebook PDF at roughly a 1-in-7 rate across repeated test runs, seemingly pre-existing flakiness unrelated to this specific fix's logic (not reproduced on any single-column document). The app already handles a crashed conversion the same as any other failure — it shows as a failed card with a working Retry button, and retrying has so far always succeeded.

## Hybrid PDF engine: docling for non-Hebrew layouts

The whitespace-gap column-detection heuristic above (`_detect_column_gutter` / `_detect_row_bands`) has a real ceiling on genuinely complex layouts — magazine/guidebook-style pages with nested two-column regions, directory-style business listings, tight-set columns with no whitespace gutter at all. Confirmed against real travel-guidebook PDFs where sections still read as scrambled nonsense despite the fixes above.

For non-Hebrew PDFs, `convert_driver.py` now tries [`docling`](https://github.com/docling-project/docling) (IBM's ML-based document layout engine) first, falling back to the `markitdown` path above if `docling` raises for any reason (unsupported/corrupt PDF, missing models, a native crash):

- **Routing is Hebrew-fraction-gated, not a blanket switch.** `_estimate_hebrew_fraction()` samples a handful of pages via `pdfplumber` (adaptively widening the sample if the first pages happen to be text-sparse — see the function's docstring for why that matters) and counts Hebrew-block characters against all alphabetic characters. Documents at or above 15% Hebrew stay on the `markitdown` path unconditionally; `docling` is never even attempted for them. This is deliberate, not a temporary limitation: `docling` has a confirmed bug reversing Hebrew word order (tested directly against a Hebrew PDF this app already converts correctly; also a known upstream issue as of early 2026, [docling-project/docling#3021](https://github.com/docling-project/docling/issues/3021)), so the hand-tuned RTL handling above is intentionally kept as the only path for Hebrew content, not merely the fallback.
- **A `docling` failure on a non-Hebrew PDF is silent and non-fatal** — it falls back to `markitdown` with nothing written to stderr; only a failure of *both* engines is treated as fatal. This matters because `docling`'s dependency stack (PyTorch, ONNX Runtime, RapidOCR) is large and more failure-prone than `pdfplumber`, and a regression there should never break a conversion that used to work.
- **Verified improvement**: on a real multi-region "Contents" table-of-contents page (a features list, a resources list, and a sidebar box interleaved across two columns) that the heuristic approach could never fully untangle, `docling`'s output reads in correct, fully linear order. Also verified on a 128-page guidebook page where the column-gutter heuristic found no whitespace gap at all (a tight-set layout) — `docling` still produced fluent, correctly-ordered prose there.
- **OCR bonus**: `docling` bundles real OCR (RapidOCR), so scanned/image-only PDFs — previously reported by this app as "nothing extractable, needs OCR" with zero recovered text — now actually get text back. Tested against a genuinely scanned 76-page travel planner (zero text characters, one full-page image per page): recovered ~223,000 characters of markdown, the large majority clean and directly usable (business listings, addresses, phone numbers came through correctly), with isolated garbled stretches (roughly 3% of non-empty lines in a rough spot-check) around at least one stylized/decorative page element. Not perfect, but a real, substantial gap closed compared to recovering nothing at all.

**Fully offline**: `docling`'s model weights (~500MB, Hugging Face Hub) and RapidOCR's own models (~30MB, downloaded straight into the installed `rapidocr` package directory) are pre-downloaded at *build* time — `build_python_runtime.sh` runs one throwaway conversion with `HF_HOME` redirected to `build/hf-cache`, and `build_app.sh` copies that cache into `Contents/Resources/hf-cache` alongside `python-runtime`. At runtime, `convert_driver.py` points `HF_HOME` at the bundled cache (packaged app: sibling `hf-cache` next to itself in `Resources/`; dev layout: `build/hf-cache`) and sets `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1` before `docling` is imported, so it never attempts a network request — verified by running a conversion through the built app with the network proxy pointed at an unreachable address (fails fast rather than hanging) and by polling open sockets on the Python process during a live conversion (`lsof -p <pid> -i`, no connections observed).

This substantially grows the bundled runtime: PyTorch + `docling`'s own dependencies add roughly 1.2GB to `python-runtime` on top of what `markitdown`'s extras need, plus the ~530MB model cache — pushing `MarkItDown.app` from tens of MB to roughly 2.6GB total. Expected and accepted as the cost of fully offline ML-based layout analysis.

**`docling` runs in its own process.** The driver starts a second copy of itself (`convert_driver.py --docling-worker <file>`) for the `docling` conversion and reads the Markdown back. The fallback to `markitdown` used to cover Python exceptions only: a crash inside `docling`'s native libraries (SIGSEGV, seen on four of eight conversions of a 76-page document while the machine was short of memory) killed the driver itself, fallback included, and the app reported "Conversion failed". Now only the worker dies and the driver falls back. If the driver is stopped (the app's timeout, or removing a card) it stops the worker first, and a worker whose driver has disappeared exits within a second. Checked by staging the crash (a stand-in `docling` that kills its process on import), which is also a standing regression check, and by sending the driver SIGTERM and SIGKILL with a worker running.

**Scope note**: this routing currently applies to `.pdf` files only — DOCX/PPTX/XLSX/etc. are unaffected and still go through `MarkItDown().convert()` exactly as before. Extending the same pattern to other formats is a reasonable follow-up if `docling`'s layout handling would help there too, but was out of scope here.

## Known gaps / deferred

- **OCR / image captioning is not wired up for non-PDF files.** The upstream `markitdown-ocr` companion package requires the caller to supply their own LLM vision client and was out of scope for this v1 — dropping a standalone image in still gets you EXIF/metadata only. PDFs are a partial exception now: `docling`'s bundled OCR (see above) recovers text from scanned/image-only PDFs, but a real text description of a *diagram's contents* (as opposed to reading text that happens to be in a scanned image) is still not available anywhere in the app.
- **Azure Document Intelligence / Azure AI Content Understanding are not included.** The upstream `all` extra pulls these in, but they require Azure cloud credentials and are irrelevant for local/offline use, so they were skipped entirely (not installed into the runtime, and their converters will simply fail to import if invoked).
- **Transcription removed (0.2.0).** markitdown's audio transcriber (`SpeechRecognition.recognize_google`) uploads the recording to Google's speech API, and the YouTube transcript fetcher calls YouTube, both of which contradict the offline/private design. The `audio-transcription` and `youtube-transcription` extras are no longer installed (the `SpeechRecognition`, `pydub` and `youtube-transcript-api` packages are absent from the runtime, so audio inside a ZIP is skipped instead of uploaded), `convert_driver.py` refuses audio files with an explanatory message, and `tests/regression_test.py` fails if any of those packages ever reappears in the runtime. For offline transcription the route would be a local model (e.g. Whisper), which is a separate piece of work.
- No file-type/size validation before handing a file to markitdown; very large files will simply take longer (or fail with whatever error markitdown itself raises). Files are converted one at a time, in the order they were added (each conversion is its own Python process, and a `docling`-routed PDF loads its models into it); a card shows "Waiting to convert…" until its turn. A conversion still running after 30 minutes is stopped and reported as failed (`ConversionService.conversionTimeout`; the slowest legitimate one measured took about 8.5 minutes), and removing a card stops its conversion.

## Testing performed

- `tools/build_app.sh` was run end-to-end successfully (Swift release build, Python runtime download + `pip install` of the vendored package with all listed extras, app bundle assembly, ad-hoc codesign).
- The bundled Python + `convert_driver.py` was exercised directly (independent of the Swift app) against a `.txt`, an `.html` file (headings, a link, a table), and a `.csv` file — all produced correct Markdown on stdout. A conversion against a non-existent path was also checked, confirming the non-zero exit code and a clear message on stderr.
- The packaged app was launched (`open build/MarkItDown.app`), confirmed running via `pgrep -f MarkItDownMac`, and quit cleanly via AppleScript.
- Drag-and-drop and the app's rendered UI were confirmed manually (screenshot + a real Finder drag), after an earlier session couldn't get Screen Recording permission or simulate OS-level drag-and-drop.
- A real-world Hebrew PDF (a right-to-left magazine article, 7 pages) was used to catch and fix the RTL text-mirroring bug described above — verified against the actual rendered PDF page (via `pdftoppm`) to confirm correct word/character order, mixed-language content (embedded English acronyms, numbers, photo credits), and multi-page consistency, run through the full `convert_driver.py` → `MarkItDown` pipeline exactly as the app itself invokes it.
- A second real-world Hebrew PDF (a 39-page math worksheet booklet, compiled from mixed sources/fonts) surfaced the font-encoding swap bug and a case where the two RTL bugs compound on the same line, described above. Regression-tested against the *first* Hebrew PDF after each fix (an automated scan of both full documents for Hebrew orthography-rule violations, not just eyeballing a few lines) to make sure fixing one document's bug didn't silently break the other's already-correct text — this caught two real regressions during development before they shipped.
- **Hybrid docling routing** (see above) was verified with a full `FORCE_REBUILD=1 ./tools/build_app.sh`, then: (1) all three real Hebrew PDFs used to develop the RTL fixes were re-run through the built app's bundled `convert_driver.py` and scored for orthography-rule violations — all three matched their known counts exactly (40 / 0 / 6), confirming Hebrew routing and output are unaffected; (2) three real English travel-guide PDFs (a nested-two-column table of contents, a 128-page guidebook with a page the whitespace-gutter heuristic couldn't split at all, and a 76-page fully scanned travel planner) were converted end-to-end and spot-checked against the actual source content — all read correctly, including the OCR path recovering ~223,000 characters of mostly-clean text from a document that previously yielded nothing; (3) offline operation was verified by running a built-app conversion with the network proxy pointed at an unreachable address (succeeds immediately, doesn't hang or error) and by polling `lsof -p <pid> -i` on the Python process during a live conversion (no connections observed); (4) a `.html` conversion confirmed the non-PDF `MarkItDown().convert()` path is unaffected. One real bug was caught and fixed during this testing: an initial fixed 5-page Hebrew-fraction sample landed entirely on a structurally text-sparse stretch of the math-worksheet PDF (image-based numerals, near-empty pages) and scored 0% Hebrew, misrouting a Hebrew document to `docling` — fixed by making the sample adaptive (widens until it collects a minimum amount of alphabetic signal, capped for speed). A second bug — a `docling` internal component (`docling_ibm_models`' table-matching post-processor) logging WARNINGs to stdout rather than stderr, corrupting this driver's JSON output — was also caught and fixed by redirecting both stdout and stderr (not just stderr) for the duration of the `docling` call.
